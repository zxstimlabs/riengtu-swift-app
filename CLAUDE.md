# Riengtu

SwiftUI app for iPhone and iPad, in English and Vietnamese. See README.md for setup and layout.

## Conventions
- The Xcode project is generated by XcodeGen from `project.yml` and not committed. Run `xcodegen generate` after adding or removing files.
- UI lives in `App/`. Everything that isn't UI lives in `Packages/RiengtuKit`, with tests (`swift test`).
- iOS only for now: the one target has `supportedDestinations: [iOS]`. Put iOS-only APIs (UIKit) behind `#if os(iOS)`, so a native Mac build can come later by adding `macOS` there, as in Figbear and ETHnym. Check that it compiles with `-destination 'generic/platform=iOS Simulator'`. To run it, pick a simulator by name and OS from `xcrun simctl list devices available`, since a name alone can match more than one runtime.
- Swift 6 language mode, iOS 18 deployment target. The app target defaults to main-actor isolation. RiengtuKit has no default isolation.
- Give `FileManager` paths as `url.path(percentEncoded: false)`, never `url.path()`, which percent-encodes the space in "Application Support". The Simulator skips file protection, so a wrong path there can still work and only fail on a device (build 6 opened to a blank screen this way).

## Privacy and money
- Riengtu is a private money app: a ledger of money in and out, and assets such as cash, bank accounts, Vietnamese stocks, gold and property. It has no analytics or third-party SDKs, and makes no network requests except iCloud sync, which the person turns on (`CloudSync`). GRDB, which runs SQLite, is the one library, by the user's choice. Keep it that way unless the user asks otherwise.
- Stock, fund, gold and crypto prices are typed in for now. The user plans to fetch them from their own server later, which will fill in `Asset.Value`'s price and `valuedAt`.
- The data stays in the ledger database (`LedgerDatabase`, complete file protection, `secure_delete`) and, with sync on, in the person's private iCloud database, encrypted end to end. Don't put ledger data in `UserDefaults`, logs or anywhere else. `Logger` messages mustn't include amounts or notes.
- Change the ledger only through `LedgerStore`, which saves before it shows a change, and refuses to save over data it couldn't read.
- Apply `.privacyShield()` to the root of every sheet or full-screen cover, as well as `RootView`, or the sheet shows above the lock screen.
- The ledger's entries (`Entry`) are expenses, income, transfers between the person's own assets, and adjustments. Money moved between their own accounts, cash, savings, investments or e-wallets is a transfer, never an expense or income.
- Expense categories (`ExpenseCategory`) are spending only, and income categories (`IncomeCategory`) income only. A new category needs a new `LedgerDatabase.RecordVersion.entry` (see Storage and sync), a name in both languages, and a symbol that's in iOS 18.0. A new expense category also needs a line in `ExpenseTagger.categoryDescription` (a test checks).
- An expense can name the account it came from and income the account it went to (a money asset), and a transfer takes from one asset and adds to another: money, or a quantity of shares, units or coins, or a weight of gold. An expense's or income's currency is its account's.
- Entries never change an asset. An asset keeps the value set by hand, as of `valuedAt`, and what it holds now is computed (`Ledger.current(_:at:)`): that value with the changes of the entries dated after it, up to now. So editing or deleting an entry needs no undoing, and entries from two devices both count. Show and total assets with `current` (`assetSections()`, `assetTotals()`), never `asset(id:)` alone. Balances can go below zero.
- The asset editor shows the current value. Saving it unchanged keeps the value set by hand and its date; changing it sets a new value as of now, and records an adjustment (`Ledger.save(_:recordingChangeOn:)`) from the current worth to the new one. Deleting an adjustment leaves the asset as it is. Prices fetched automatically, when that comes, must save without a date, or they'll fill the ledger. Deleting an asset deletes its adjustments; other entries keep pointing at it and show it as removed.
- Each entry and asset has its own currency. Never add amounts in different currencies together. Assets are totaled per currency (`Ledger.assetTotals`), and so is each month's income and spending (`Ledger.flows`), which leaves out transfers and adjustments. No budgets for now, by the user's choice.
- Amounts are `Decimal`. Format them with `.currency(code:)`, and type them in a `NumberField`, which uses `AmountInput`. Don't read separators from `Locale.decimalSeparator`: it follows the Number Format chosen in Settings, which `FormatStyle` ignores (see `AmountInput.decimalSeparator`).

## Storage and sync
- `LedgerDatabase` (GRDB) keeps each entry, asset and tag as one row of `record`: its JSON (the types' `Codable`), its format's version, `modifiedAt`, and the CloudKit system fields. `CloudRecord` makes the same row a CloudKit record, its JSON in an encrypted field. Builds before the database kept a JSON file (`LedgerFile`); `LedgerStore.load()` moves it in once and deletes it.
- Raise `LedgerDatabase.RecordVersion` for a record type when an earlier version would misread or lose part of it: a new kind of entry, a new category, a new field. Earlier versions show a newer record without changing it (`Ledger.newerIDs`, `LedgerStore.NewerVersionError`), or keep one they can't decode as it is (`Ledger.unreadableRecordCount`). Never make an earlier version refuse the whole ledger.
- Migrations only add tables, or columns with defaults: an earlier version may open the database after a later one, and keeps using the tables it knows.
- `CloudSync` runs Apple's `CKSyncEngine` in the private database's `Ledger` zone, container `iCloud.vn.riengtu`. It runs only while the app is active, since the database can't be opened once the device locks. Every change is marked in the database (`needsUpload`, `tombstone`) until iCloud has it, so nothing's lost when the engine stops. The later `modifiedAt` wins a conflict, except that an older format never replaces a newer one. If the iCloud account changes or the zone is deleted elsewhere, syncing turns off and the device keeps its data. Erase All Data deletes the zone first, and erases nothing if it can't.
- `swift test` can't reach iCloud: it tests the database's merge rules and `CloudRecord`. Try syncing on two devices signed in to the same iCloud account with a signed build. Before a TestFlight or App Store build syncs, deploy the CloudKit schema from Development to Production in the CloudKit Console.

## Tags and Apple Intelligence
- Expenses and income have tags for what the money was for. Transfers don't. The starter tags (`Tags.starter`) are stored in English and shown in the app's language with `Tags.displayName`. Tags the person makes are stored and shown as typed. Pass every name the person types through `Tags.stored`, so "Công việc" stays the starter tag "Work".
- `ExpenseTagger` suggests an expense's category and tags with the Apple Intelligence model on the device. It doesn't run for income or transfers. Use only `SystemLanguageModel`, never `PrivateCloudComputeLanguageModel` or any other model that leaves the device. Never log notes or the model's answers.
- The app must work fully without the model: on iOS 18, on devices without Apple Intelligence, and with it off. Check `ExpenseTagger.availability` first. Suggestions are only ever shown for the person to tap, except the category, which is filled in only until the person picks one. `FoundationModels` is weakly linked (`project.yml`).
- The instructions were tuned on sample notes: the general model beats the content-tagging one here, and the "none" choice stops it tagging everything. Re-run sample notes after changing them. `swift test` runs the real model on a Mac with Apple Intelligence on. The iOS 26.3 simulator can't load the model's safety check and fails every request; use an iOS 27 simulator or a device.

## Inbox
- Money in and out captured by the Shortcuts actions (`App/Capture`) goes to `InboxStore`, never straight into the ledger. A bank message about money received is kept too (`CapturedTransaction.isMoneyIn`) and opens as income. The inbox has its own file, protected until first unlock, because the actions run in the background while the device may be locked, when the ledger can't be opened.
- The actions' replies can show on the Lock Screen: never put amounts, names or notes in them.
- App Store Connect rejects a build whose App Intent titles or descriptions contain "Apple" in any language (ITMS-90626), so write "a card in Wallet", not "Apple Pay", there.
- The card payment shortcut is shared from an iCloud link (`CaptureHelpView.cardPaymentShortcut`). The link is a copy of the shortcut: after changing the shortcut or `CapturePaymentIntent`'s parameters, the user rebuilds and shares it again, and the link is replaced.
- An action's parameters that can be missing in an automation must be optional. A required one without a value makes the action ask for it, which fails in the background. Run `IntentTests` (README) after changing an action.
- `TransactionText` (rules) reads a message at capture. `TransactionReader` (Apple Intelligence) reads it only while the app is open. Prefer the rules' amount: the model sometimes gives the balance. Add new bank formats to `TransactionTextTests`, with account numbers and names changed.

## Two languages
- Every string the app shows is in English and Vietnamese, in `App/Localizable.xcstrings`. English is the source language and the keys are the English text.
- Write UI text as literals SwiftUI localizes: `Text("…")`, `Button("…")`, `Label("…", systemImage:)`, `.navigationTitle("…")`. Where an API takes a plain `String`, use `String(localized: "…")`. Never put a `String` variable into `Text` and expect it translated.
- One key per whole sentence. Don't build sentences from pieces, because Vietnamese word order differs. Put values in with interpolation (`Text("\(count) photos")`), and give English plural variations in the catalog. Vietnamese has no plural forms, so it needs only one.
- Add the Vietnamese with every new string. `swift test` fails on any string that's missing it or not marked translated (`StringCatalogTests`).
- A build in the Xcode IDE adds new strings to the catalog, but `xcodebuild build` doesn't. From the command line, `xcodebuild -exportLocalizations -project Riengtu.xcodeproj -scheme Riengtu -localizationPath build/loc -exportLanguage vi -derivedDataPath build` adds them (empty, so the test then names them), or add the keys by hand.
- RiengtuKit returns data, not user-facing text, so it has no string catalog. The app turns Kit values into words. `AppLanguage.endonym` is the exception: a language's name in itself, which no one translates.
- Check screens in both languages. Launch with `-AppleLanguages "(vi)"` (README). Vietnamese usually runs longer than English and stacks diacritics (ễ, ặ), so look for truncation and clipped lines, and don't hard-code widths or line heights around text.
- The language comes from iOS: the device's language, or the one picked for Riengtu in Settings. There's no in-app switch. Settings > Change Language opens the app's page in Settings.
